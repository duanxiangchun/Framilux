# 01 · 架构设计

## 1. 设计原则

| # | 原则 | 原因 |
|---|---|---|
| P1 | **离线优先** | 实时引导对延迟极敏感，且是最强的隐私卖点。Android 侧干脆不声明 INTERNET 权限 |
| P2 | **快慢双通路** | 实时引导只用毫秒级模型；昂贵但有用的信息（深度、法线、美学）走低频通路 |
| P3 | **单帧多模型共享预处理** | 一次解码/缩放生成多个分辨率桶，避免每个模型各自 resize |
| P4 | **模型可替换** | 所有感知模型藏在 `Perceptor` 接口后，允许换模型、换后端（GPU/NPU/CPU）而不改业务 |
| P5 | **纯逻辑可单测** | 规则、打分、求解不依赖相机与图形 API，能在 JVM 上跑单测，也能移植到 iOS/Web |
| P6 | **先平滑再上屏** | 任何逐帧输出都要过 EMA + 迟滞状态机，否则提示会跳变到不可用 |

## 2. 分层总览

```
┌──────────────────────────────────────────────────────────────────┐
│ L5 交互层    取景 UI / 快门 / 设置 / 拍后评审页 / (debug) 调参面板    │
├──────────────────────────────────────────────────────────────────┤
│ L4 引导渲染  GuidanceRenderer：箭头 / 目标虚影框 / 水平仪 / 三分线   │
│              主体框 / 姿势虚影 / 单句文字                            │
├──────────────────────────────────────────────────────────────────┤
│ L3 决策层    FusionEngine → SceneProfiler → RuleEngine → ScoreEngine │
│              → GuidanceSolver            （纯逻辑，无平台依赖）      │
├──────────────────────────────────────────────────────────────────┤
│ L2 感知层    PerceptionBus：Face / Pose / Saliency / Lines / Scene   │
│              / LightStats （fast）  Depth / Normal （slow）          │
│              统一输出 PerceptionFrame（归一化坐标）                   │
├──────────────────────────────────────────────────────────────────┤
│ L1 预处理    FrameGate（节流/丢帧）→ GPU resize → 分辨率桶 384/256/224│
│              YUV→RGB、旋转对齐、归一化、缓冲复用                      │
├──────────────────────────────────────────────────────────────────┤
│ L0 采集层    CameraX：Preview + ImageAnalysis + ImageCapture         │
│              IMU（陀螺/加速度）采样、镜头信息（等效焦距/数码变焦）      │
└──────────────────────────────────────────────────────────────────┘
横切关注点：ModelRegistry/模型生命周期、性能与热管理、日志与指标、隐私
```

## 3. 一帧的生命周期

```
CameraX ImageAnalysis (YUV_420_888, 1280x720 @30fps)
  │
  ├─[FrameGate] 节流到 10fps；若上一帧仍在推理，直接丢弃本帧（只保留最新）
  │
  ├─[Preprocess] GPU: YUV→RGB → 旋转/镜像 → 缩放为 384²、256²、224² 三个桶（缓冲池复用）
  │
  ├─[PerceptionBus] 并行提交（同一 GPU 队列串行执行，CPU 侧并行）：
  │    384² → YuNet(人脸 4ms) / RTMPose-s(姿态 4ms) / M-LSD-tiny(直线 2ms)
  │    256² → UniSal(显著图 3ms)
  │    224² → Places365(场景 2ms)
  │    CPU  → LightStats(直方图/色温/溢出，< 1ms)
  │    ─────────────────────────────────── 合计 ≈ 15 ms
  │
  ├─[SlowPath Worker, 每 500ms 一次] Metric3D(深度 44ms) + DSINE(法线) → 追加到最新快照
  │
  ├─[FusionEngine] 收集各感知结果 → PerceptionFrame（归一化坐标 + IMU 位姿 + 时间戳）
  │
  ├─[Decision] SceneProfiler → 权重向量 w
  │            RuleEngine    → 各规则得分 f_i ∈ [0,1] + 局部建议
  │            ScoreEngine   → score = Σ w_i·f_i → 映射到 0–5 分
  │            GuidanceSolver→ Δpan / Δtilt / Δzoom / Δroll + 目标框 + 文字
  │
  ├─[Smoother] EMA + 迟滞 → GuidanceSnapshot（不可变，供 UI 读取）
  │
  └─[Renderer @30–60fps] 读取最新快照渲染叠加层（与推理帧率解耦）
```

快门按下后走独立的 **PostCapture 通路**：
```
ImageCapture(全分辨率 JPEG/RAW)
  → NIMA aesthetic + technical（各 ~173ms，仅一次）
  → 裁剪建议（复用 RuleEngine 在候选裁剪窗上搜索最优）
  → 可选：LUT / 低光增强 / 端侧 VLM 一句话点评
  → 评审页：原图 vs 建议构图对照 + 分项得分
```

## 4. 三条通路的预算与频率

| 通路 | 频率 | 延迟预算 | 内容 |
|---|---|---|---|
| Fast（实时引导） | 10 fps | ≤ 25 ms 推理 / ≤ 100 ms 端到端 | 人脸、姿态、显著、直线、场景、光照统计 |
| Slow（增强感知） | 2 fps（可降到 0.5 fps） | ≤ 60 ms，异步不阻塞 UI | 深度、法线 → 光位与空间层次 |
| Post（拍后） | 每张一次 | ≤ 1.5 s | 美学/技术评分、裁剪建议、调色、可选 VLM |

## 5. 线程与并发模型

```
CameraExecutor(单线程)         ── 采集回调，只做入队与丢帧判定
GpuInferenceDispatcher(单线程) ── 所有模型推理串行（GPU/NPU 资源独占），保证延迟可预测
CpuWorkerPool(2~3 线程)        ── 直方图、坐标变换、规则引擎（若 GPU 空闲可并行）
SlowPathWorker(1 线程)         ── 每 500ms 触发一次昂贵模型
PostCaptureWorker(1 线程)      ── 快门后的重活
MainThread                     ── 只做渲染与 UI 状态
```

**数据交换用"最新快照"而非队列**：感知结果发布到 `AtomicReference<PerceptionFrame>`，决策层按固定节奏读取最新值；UI 读 `AtomicReference<GuidanceSnapshot>`。这样任何一环慢都不会造成延迟堆积（背压策略 = 丢旧帧，而不是排队）。

## 6. 时间戳与传感器对齐

引导求解必须知道**当前画面拍摄时手机的姿态**，否则水平仪和箭头方向会错。

- 每个 `ImageProxy` 的 `timestamp` 与 IMU 采样（`SensorManager` 陀螺/加速度，100 Hz）都打到同一个单调时钟上
- 取"与帧时间戳最接近且不晚于它的 IMU 样本"，线性插值出 roll / pitch / yaw
- 同时记录镜头信息（等效焦距、数码变焦倍率）：变焦会改变"该靠近还是该退后"的换算
- 推理是异步的，因此 `PerceptionFrame.tsNs` 记录的是**采集时刻**，不是推理完成时刻；决策层据此做时间一致性校验（超过 200ms 的旧帧直接丢弃）

## 7. 平滑、迟滞与引导状态机

- **EMA 平滑**：所有连续量（主体框、倾角、建议位移）经 `x ← α·x_new + (1-α)·x_prev`，α 取 0.3–0.5（实测调参项）
- **迟滞（Hysteresis）**：主建议只有在新方案得分超过当前方案一定阈值（如 +0.08）时才切换，避免两条建议来回闪
- **最短展示时长**：一条文字建议至少展示 1.2s，防止闪烁
- **引导状态机**：

```
Idle ──(打开相机)──► Guiding ⇄ Scanning ──(快门)──► Capturing ──► Review ──► Guiding
                        │                              │
                        └──(连续 1.5s 得分 > 4.2)──────┘ 触发"可以拍了"提示
```

`Scanning` 是"一键扫描分析"模式：暂停实时更新，抓一帧高分图跑完整链路（含慢通路），一次性给出结论与建议模板。

## 8. 性能预算（中端机目标）

| 阶段 | 预算 | 备注 |
|---|---|---|
| 采集 → 回调 | 8 ms | CameraX 自身开销 |
| 预处理（GPU） | 5 ms | 三桶共享一次解码 |
| 感知推理（串行） | 15 ms | 见上表 |
| 融合 + 规则 + 求解 | 2 ms | 纯 CPU 数学 |
| 平滑 + 快照发布 | < 1 ms | |
| 渲染叠加层 | 16 ms | 与 30fps 刷新解耦 |
| **端到端（帧采集 → 提示上屏）** | **≤ 100 ms** | 实测目标 |

内存：预分配三档输入缓冲 + 显著图缓冲，稳态零分配；模型常驻显存约 60–80 MB（按 manifest 中 selected 模型估算）。

## 9. 模块映射

| 层 | Android 模块 | 是否可跨平台 |
|---|---|---|
| L0 采集 | `core-capture` | 否（平台相关，接口化） |
| L1 预处理 | `core-capture` + LiteRT 预处理扩展 | 部分 |
| L2 感知 | `core-perception` | 否（模型运行时相关），但输出契约可共享 |
| L3 决策 | `core-composition` | **是（纯 Kotlin/TS 双实现）** |
| L4 渲染 | `feature-guidance` | 否 |
| L5 交互 | `feature-camera` / `app` | 否 |

## 10. 平台抽象

决策层只认 `PerceptionFrame`，不认模型。因此：

- Android：CameraX + LiteRT → `PerceptionFrame`
- Web 原型：getUserMedia + onnxruntime-web/MediaPipe → 同一份 `PerceptionFrame`（TS 定义）
- iOS（远期）：AVFoundation + Core ML → 同一份契约

三端共享的是**契约与规则**（`docs/04-interface-contracts.md`），不是二进制。

## 11. 降级策略

按温度与负载逐级降档，保证"永远有反馈"：

| 级别 | 触发条件 | 行为 |
|---|---|---|
| L0 | 正常 | 全功能 |
| L1 | 温升中等 / 帧时间超预算 | 慢通路降到 0.5 fps |
| L2 | 持续超预算 | 直线与场景降到 2 fps，复用上次结果 |
| L3 | 高温 / 低端机 | 只保留人脸 + 显著性 + IMU |
| L4 | 极端 | 关闭全部推理，只留静态三分线 + 传感器水平仪 |

其他失败处理：模型加载失败 → 该规则自动失效并在 debug 面板标注（不崩溃）；显著性不可用 → 用"人脸 ∪ 最大前景块的视觉重心"降级替代。

## 12. 隐私

- Android 不声明 `INTERNET`；不写任何网络调用代码
- 相机帧只存在于内存缓冲，不落盘（除用户主动拍摄）
- 日志与调参面板仅在 debug 构建启用，release 不采集任何数据

## 13. 被否决的方案（以及为什么）

| 方案 | 否决原因 |
|---|---|
| 用 MediaPipe Tasks 全家桶做感知 | 官方包缺显著性、直线检测、美学评分；自定义模型接入不如 LiteRT 直接。降级为 fallback |
| 用端侧 VLM 做实时构图建议 | 延迟与空间定位精度都不达标。仅保留为低频"一句话点评" |
| 单个大模型端到端出建议 | 无现成权重、不可解释、无法分级降档；工程上不可控 |
| 云端推理 | 违背离线与隐私定位，且弱网下不可用 |
| 全模型每帧串行 | 累计超预算，低端机直接塌 |
| 用队列缓冲感知任务 | 延迟堆积，用户手都停了提示还在追。改用"最新快照 + 丢旧帧" |
